⚡ Process Sharding & Data Partitioning

Veloctra implements a 5-layer sharding and partitioning architecture designed to guarantee non-blocking high throughput, sub-second backpressure, and zero data loss.

1. Source-Level Cursor & Range Sharding

When reading large relational tables or file buckets, Veloctra streams records via server-side cursors and watermark range queries without loading full tables into memory:

-- Incremental cursor range partitioning
SELECT * FROM raw_claim_benef 
WHERE id >= :start_id AND id < :end_id 
ORDER BY id ASC;

2. Adaptive In-Flight Memory Sharding (MemoryGuard)

The MemoryGuard continuously monitors process RAM, OS CPU, and individual record sizes:

Massive Records (≥ 5 MB/row)

Chunk size is immediately reduced to 1 record per chunk to prevent memory spikes.

Large Records (≥ 100 KB/row)

Chunk size is throttled down to 50 records per chunk.

Resource Ceiling (> 75% RAM/CPU)

Chunk sizes are halved and micro-sleep backpressure is applied, leaving ≥ 25% headroom for Python Garbage Collection.

3. Horizontal Process & Job Sharding

Pipelines execute as decoupled asynchronous worker tasks identified by unique job_id strings (e.g. csv_to_postgres_4). Multiple jobs execute simultaneously across available CPU cores, completely isolated by tenant ID.

4. Fault-Isolation Sub-Chunking (DLQ Routing)

If a vectorised PyArrow batch of 10,000 rows encounters corrupt data, the orchestrator sub-shards the batch row-by-row (batch.slice(i, 1)). The poison-pill record is routed to the MongoDB Dead Letter Queue (dlq) with full stack trace, while all valid rows proceed immediately.

5. Destination File Sink Partitioning (FilePartitioner)

High-throughput data exports are partitioned into numbered files (part_00001.parquet, part_00002.parquet) whenever:

  • Row count reaches max_rows_per_file (default: 100,000 rows).
  • Memory volume reaches max_file_size_mb (default: 100 MB).
